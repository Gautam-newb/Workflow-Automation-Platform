## Workflow Automation Platform Runbook

This runbook describes how to diagnose and remediate common failure modes in the Workflow Automation Platform.

The platform consists of:
- n8n workflow(s)
- API Gateway `POST /webhook` endpoint managed by Serverless Framework
- Lambda function `workflowHandler` (Python 3.10)
- Optional S3 output bucket for persistence
- CloudWatch Logs for observability

---

### Validation failures

**Symptoms**
- API Gateway returns HTTP `400` responses.
- Lambda logs contain `event: "validation_failed"` entries.
- Error messages such as `Missing required_field in payload` or `Request body must be valid JSON`.

**Diagnosis steps**
- In CloudWatch Logs, filter for `workflow_received` and `validation_failed` events using the `request_id` from the API response.
- Verify that n8n is sending JSON with the `required_field` key.
- Check for malformed JSON in the n8n webhook node.

**Remediation**
- Update the n8n workflow to always include `required_field` in the request body.
- Add validation or defaulting logic on the n8n side before calling the API Gateway endpoint.
- Re-run the workflow and confirm that responses are now HTTP `200`.

---

### Lambda failure

**Symptoms**
- API Gateway returns HTTP `500` responses.
- CloudWatch Logs show `event: "workflow_error"` with stack traces.

**Diagnosis steps**
- In CloudWatch Logs, search for the `request_id` from the failing response.
- Review the stack trace under `workflow_error` for the failing code path.
- Check for recent code changes or configuration changes that could affect the Lambda (e.g., new environment variables).

**Remediation**
- Fix the underlying bug in the Lambda handler (e.g., missing key handling, unexpected data shape).
- Add or adjust unit tests (pytest) to cover the failing scenario.
- Redeploy via Serverless (see README “How to deploy”).
- Re-run the workflow and verify successful `200` responses.

---

### IAM permission issue

**Symptoms**
- Lambda responses are still `200`, but S3 output objects are missing.
- CloudWatch Logs contain `event: "s3_persist_failure"` with errors like `AccessDenied` or `AccessDeniedException`.

**Diagnosis steps**
- In CloudWatch Logs, filter for `s3_persist_failure` to confirm permission-related errors.
- Validate the value of `S3_OUTPUT_BUCKET` in Lambda environment variables.
- Inspect the IAM role generated by Serverless to ensure it includes:
  - Action: `s3:PutObject`
  - Resource: `arn:aws:s3:::<bucket-name>/*`

**Remediation**
- Update `serverless.yml` IAM role statements if necessary and redeploy.
- Ensure the S3 bucket policy allows the Lambda role to `PutObject`.
- Re-run the workflow and confirm that S3 objects are created.

### Retry strategy

The Lambda function is **retry-safe** and designed for idempotent persistence:

- The S3 object key is derived from the `request_id`. On retries with the same `request_id`, the same object key is overwritten, which is safe.
- Validation failures (`400`) should not be retried automatically; fix the request payload first.
- Transient infrastructure issues (e.g., S3 timeouts) may be retried by the caller (n8n) or by re-running the workflow manually.

**Operator guidance**
- For `400` errors: do **not** retry automatically; correct the workflow payload.
- For `500` errors: investigate the root cause in CloudWatch Logs, deploy a fix, then retry.
- For `s3_persist_failure` with otherwise successful responses: you may re-drive the affected payloads by replaying them from logs or from n8n history.

---

### Rollback steps

If a deployment causes widespread failures (e.g., all requests start returning `500`):

1. **Freeze changes**
   - Stop merging new PRs to `main`.
   - Communicate the incident and current status to stakeholders.

2. **Identify last known good version**
   - Use `git log` to identify the last commit where the platform was stable.
   - Optionally, tag stable releases (e.g., `v1.0.0`) for easier rollbacks.

3. **Rollback via Serverless**
   - Check out the last known good commit locally (or use a dedicated rollback branch).
   - Run `serverless deploy --stage prod` from that commit to redeploy the stable Lambda and configuration.

4. **Validate**
   - Execute the example webhook payload from the README.
   - Confirm HTTP `200` responses and expected S3 persistence.
   - Monitor CloudWatch Logs for absence of new errors.

5. **Post-incident actions**
   - Perform root cause analysis and capture findings.
   - Add or extend unit tests and monitoring to prevent recurrence.
   - Plan a forward fix and a controlled redeployment.
